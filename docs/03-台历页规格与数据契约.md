# 03 · 台历页规格与数据契约

> 目标：Zectrix Note4（ESP32-S3 · 400×300 墨水屏）上每天凌晨自动刷新一页台历，
> 显示 **当天日期 / 班次时段 / 今日班次**，并附带**农历、节气、节日、星期**。
>
> 本文是**固件实现的对照规格**。**版式（§1–§4）与取数策略（§6）均已定稿**，
> 权威渲染器是 `tools/calendar_A_final.py` —— 改版式先改它，再同步本文。
> 改完跑 `tools/regress_top_single.py` 做**顶栏回归**（拿旧实现重放单节日那天，
> 逐像素比对新实现，确认多签改动没有动到单节日的外观）。

---

## 1. 版式（定稿）

```
      ┌────────────────────────────────────────────────────┐
      │ 2026年9月23日                      八月十三        │  顶栏  左：年/月/日 pt28
      │                              〔中秋节〕〔国庆节〕   │        右：农历 pt21 + 节日反白签 pt18
      ├──────────────────────────────┬─────────────────────┤            （同日多个节日 → 并排）
      │                              │    星   │   秋      │
      │  上午08:00-12:00             │    期   │   分      │  主区  左：两段时段 pt25（前缀按开始时间）
      │  下午14:00-18:00             │         │           │        右：竖排星期 pt44
      │                              │         │           │            + 竖排节气 pt31（有才画）
      ├──────────────────────────────┴─────────────────────┤
      │ 今日班次                       ▓9DP0(验车)▓      │  底栏  班次名反白块 pt28（块高固定 52）
      └────────────────────────────────────────────────────┘
```

**同日多个节日** —— **全部并排展示**，各占一个独立反白签（不合并成一个）：

```
      ┌────────────────────────────────────────────────────┐
      │ 2031年10月1日                 〔中秋节〕〔国庆节〕  │  农历「八月十五」在上一行
      ├──────────────────────────────┬─────────────────────┤
```

实测 1900–2099 共 **69 天**撞车（**全部是两个、没有三个**），高频组合如
`元宵节 + 情人节`(8×)、`中秋节 + 教师节`(8×)、`中秋节 + 国庆节`(6×)、`除夕 + 情人节`(8×)。

**夜班** —— 前缀按**开始时间**自动取「夜间 / 凌晨」，不会出现「上午20:00-24:00」：

```
      │  夜间20:00-24:00             │    星   │           │
      │  凌晨00:00-04:00             │    期   │           │
```

**休息日**（班次名含「休」）—— 时段两行完全不画，主区左栏换成大字「休息」：

```
      ┌────────────────────────────────────────────────────┐
      │ 2026年6月15日                      五月初一        │  顶栏
      ├──────────────────────────────┬─────────────────────┤
      │                              │    星   │           │
      │        休  息                │    期   │           │  主区
      │        （pt72）              │         │           │
      │                              │    一   │           │
      ├──────────────────────────────┴─────────────────────┤
      │ 今日班次                             ▓休▓          │  底栏
      └────────────────────────────────────────────────────┘
```

**拉取失败**（且无本地缓存）—— 同样是时段的位置，换成「获取失败」，底栏不画班次块：

```
      ┌────────────────────────────────────────────────────┐
      │ 2026年8月8日                      六月廿六         │  顶栏（日期/农历仍由本地给出）
      ├──────────────────────────────┬─────────────────────┤
      │                              │    星   │           │
      │        获取失败              │    期   │           │  主区
      │        （pt30）              │         │           │
      │                              │    六   │           │
      ├──────────────────────────────┴─────────────────────┤
      │ 今日班次                                            │  底栏（不画班次块）
      └────────────────────────────────────────────────────┘
```

### 电量展示

电量标识位于主区右上方、星期文字上方，所有像素限制在 `x=275～383、y=62～77` 内。百分比右边缘固定为 `x=384`，垂直中心 `y=70`，字体使用 Noto Sans SC Bold pt18。电池主体 20×12 像素，右侧触点 2×4 像素，与文字间隔 6 像素，主体随文字宽度向左排列。

信号格在电池左侧，右边缘距电池 10 像素，整体 22×13 像素：四根竖条宽 4、间隔 2，高度分别 4 / 7 / 10 / 13，底边与电池底部对齐。10 像素间距是给低电量感叹号让位的，它占电池左侧 7 像素，两者之间留 3 像素空隙。

- 已连接：按 RSSI 分档点亮竖条，≥ -55 四根、≥ -65 三根、≥ -75 两根、更弱一根；已连接至少亮一根，不出现「连上了却没有格子」。
- 未连接：四根竖条都不画，改画两条交叉斜线占满 22×13 区域。4 像素宽的竖条画不出 2 像素边框的空心，空心会退化成实心，所以断开态换形状而不换填充方式。

信号格由 `CalPageInput::wifi` 驱动，为 NULL 时整块不画；`CalWifiInput.connected` 为 false 时忽略 `rssi`。

- 正常：电池内部按电量填充，百分比向下取 5% 的整数倍。
- 低电量：原始估算值低于 20% 时，在电池左侧增加静态感叹号。
- 充电：电池内部显示静态闪电，百分比保持实际估算值的 5% 步进。
- 充满：满格电池和 100%。
- 未安装电池或充电故障：空电池、感叹号和 `--%`。

固件从 `ZectrixBoard::ReadPowerSnapshot()` 读取电压与充电状态，刷新前以 100 ms 间隔读取 17 次，覆盖引脚稳定时间和交替信号窗口。ADC 测量无效时立即终止当前流程。电量随每日零点刷新、BOOT 唤醒和复位更新，深度休眠期间保持最后一次显示。渲染输入 `CalPageInput::battery` 为空时隐藏电量，供已有页面检查使用。

效果图由 `tools/calendar_A_final.py --battery-percent 75 --blank-schedule` 生成，命令参数是明确指定的预览示例值。图像与固件使用相同布局，由 `tools/battery_render_test.py` 验证全部电量状态和页面边界。

信号格的对等验证走 `tools/cal_render_test.py`：`--battery-percent` 配 `--wifi-rssi` 或 `--wifi-off`，跑全部 17 个用例逐像素比对。已覆盖四档强度（-51 / -61 / -71 / -81）、断开态、电量文字最宽的 `100%` 与最窄的 `--%`，以及低电量感叹号与信号格并存的情形。

### 顶栏多节日签的几何（实测）

| 项 | 值 | 说明 |
|---|---|---|
| 签行可用宽 | **159 px** | 标题最宽 `2026年12月31日` 墨迹右界 `x=209`，留 16px 间隙得左界 `225`；右界 `RIGHT_X=384` |
| 对齐方式 | **整行右对齐** | 右边距恒为 16px，只有左端随内容伸缩 |
| 签高 | **固定 26 px** | 2 字签与 3 字签一样高，不会一天胖一天瘦 |
| 基准档 | `pt18 / pad 10 / gap 14` | 单节日永远命中这档 → **外观与定稿逐像素一致**（已回归验证） |
| 最坏情形 | 两个 3 字节日 = 162 px **> 159** | 自动退到 `pt18 / pad 9 / gap 13` = **157 px** ✓ 余 2px |

**降级顺序：先缩内边距，后缩字号。** 反白签的黑框本身占视觉重量，缩 `pad` 比缩字号更不伤观感，
而且**不会让同一天的两个签大小不一**。档位表：

```
(18,10,14) → (18,9,13) → (18,8,12) → (17,8,12) → (16,7,11) → (15,6,10) → (14,6,9)
 字号，内边距，间隙
```

全部档位都塞不下时（实测 1900–2099 **不会发生**）才走兜底：把多个节日并成**一个**签
（`中秋节·国庆节`，分隔符 `·` 已计入字模），首字仍是优先度最高的节日。

> ⚠️ 这里也一样**不能按墨迹高二分选字号**（见下方铁律）。旧实现就踩过：
> `龙抬头` 在 pt18 下墨迹高 **19** → 被误降到 **pt17**，而 `中秋节` 保持 pt18 ——
> 同一屏上签的字号随节日名漂移。现在一律固定 pt18。

实测（`tools/calendar_A_final.py` 每次运行会打印这行自检）：

| 日期 | 节日 | 签行宽 / 预算 | 命中档位 |
|---|---|---|---|
| 2026-09-25 | 中秋节 | 74 / 159 | pt18 pad10 gap14（余 85） |
| 2031-01-01 | 元旦 + 腊八节 | 145 / 175 | pt18 pad10 gap14（余 30） |
| 2037-02-14 | 除夕 + 情人节 | 144 / 159 | pt18 pad10 gap14（余 15） |
| **2031-10-01** | **中秋节 + 国庆节** | **157 / 159** | **pt18 pad9 gap13（余 2）** ← 最坏 |

### 字号层级

**墨水屏只有黑白，没有色彩可用 → 层次只能靠「字号」和「反白」两档拉开。**

```
（常规）星期 44  >  节气 31  >  班次名 28 = 年月日 28  >  时段 25
        >  底栏标签 23  >  农历 21  >  农历(有节日时) 18 / 节日反白签 18

（休息日）「休息」72  —— 当天主区的唯一元素，压过所有层级
（失败态）「获取失败」30 —— 与时段同级，占的就是时段那两行的位置
```

**反白（黑底白字）反差最强，压过字号差异** —— 只给两个地方用：节日签、班次块。

### 字体（开源可商用）

字模源用 **Noto Sans SC**（`C:\Windows\Fonts\NotoSansSC-VF.ttf`，**SIL OFL 1.1**）。
刻意不用 Windows 自带的微软雅黑 / 等线：把字形渲染成点阵**嵌进固件**属于字体的
「复制 / 嵌入」行为，商用需授权 —— Noto / Source Han 走 OFL，没有这层约束。

⚠️ 它是**可变字体**（Weight 轴 100~900），而**这份的默认实例是极细的 Thin**，
必须显式 `set_variation_by_axes([700])` 才是 Bold。所以代码里一律经
`calendar_preview.load_font()` 取字体，**不要**直接 `ImageFont.truetype()`。
（实测 18px「中秋节」二值化后黑像素：默认实例 155 vs `wght700` 的 362 —— 前者笔画会断。）

### 五条版式规则

1. **节气有则显示、无则不占位。** 星期列位置恒定（`x=316`），节气出现或消失
   都不会让已有元素移动。
2. **清明让位。** 清明是唯一「节气即节日」的（`清明` ⊂ `清明节`），
   规则 `if 节气名 in 节日名 → 不显示节气`，避免同一天在两处各写一遍。
3. **同日多个节日全部并排。** 一个节日一个签（不合并 —— 语义上是两件事），
   整行右对齐；按重要度降序从左到右排。见上方「顶栏多节日签的几何」。
4. **休息日不画时段。** 班次名含「休」→ 主区左栏改显示「休息」大字（pt72），
   时段两行完全不画。
5. **空内容不留空壳。** 两条：
   - 班次名**为空** → **不画**反白块（否则会留下一个只有内边距的空白方块）；
   - 时段两行**都为空** → **不画**「上午」「下午」前缀，该区域留空。

   留空的原因是数据源用字段缺省表示**该天没有排班**（见 §2.2）。「获取失败」不由空内容触发，
   只在拉取失败且无可用缓存时出现（§2.4）。

### ⚠️ 字号铁律：绝不能按「墨迹高度」选字号

按**墨迹高度**二分选字号，在三类内容上都是**错的**：

| 内容 | 为什么错 | 症状 |
|---|---|---|
| **纯拉丁/数字** | 数字墨迹只占 em 的 ~71% | `9DP1` 要"墨迹高 34"会被选到 **pt44**，宽 118px，撑爆底栏 |
| **笔画少的汉字** | 「一」只有一根横画，它的"墨迹高度"其实是笔画**厚度** | 「一」要"墨迹高 40"会被选到 **pt95**，横杠 95px，是其他字的**两倍多**（「二」pt53 /「三」pt48 同理）|
| **个别汉字会差 1px** | 汉字墨迹高各不相同（`中` 在 pt18 下是 18，`龙`/`春` 是 **19**） | 同一天的两个节日签字号不一致：`龙抬头` 被降到 pt17、`中秋节` 保持 pt18 —— 顶栏一天一个样 |

**于是：任何「逐字绘制」（竖排星期、竖排节气）与「同屏并列的元素」（多个节日签）
都必须用固定 pt。**
症状不只是某个字变大 —— 是**整列每个字宽度都不一样**（实测星期列 41→95px），
竖排根本对不齐。改成固定 pt 后各字宽度极差降到 1–2px（星期 pt44 / 节气 pt31）。

「整串绘制」的区域（年月日、农历、时段、标签）没这个问题：整串共用一个字号，
中文墨迹高 ≈ em，折算误差 ≤1pt。

## 2. 数据契约

### 2.1 第三方只提供四项

| 字段 | 类型 | 含义 | 例 |
|---|---|---|---|
| `date` | `YYYY-MM-DD` | 年月日 | `2026-09-23` |
| `shift` | string | 今日班次 | `9DP1` / `9DP(绿)` / `9DP0（验车）` / `休` |
| `am` | `HH:MM-HH:MM` | **第 1 段**时段 | `08:00-12:00`；夜班为 `20:00-24:00`（**休息日忽略，可留空**） |
| `pm` | `HH:MM-HH:MM` | **第 2 段**时段 | `14:00-18:00`；夜班为 `00:00-04:00`（同上） |

```json
{
  "schema": "zectrix-note4/calendar-payload/v1",
  "days": [
    {"date": "2026-09-23", "shift": "9DP1", "am": "08:00-12:00", "pm": "14:00-18:00"}
  ]
}
```

样例见 `tools/mock_calendar_payload.json`。

### 2.2 七条处理规则

| 规则 | 做法 | 为什么 |
|---|---|---|
| **时段前缀按开始时间判定** | `<6 凌晨` / `<12 上午` / `<18 下午` / `≥18 夜间` | `am`/`pm` 的语义是「**第 1 段 / 第 2 段**」，不是真的上午下午。写死「上午/下午」会让夜班显示成**「上午20:00-24:00」** —— 实测确认过。数据源若已带前缀则识别跳过 |
| **班次名归一化** | 全角 → 半角（`9DP0（验车）` → `9DP0(验车)`） | 全角括号把宽度从 107px 顶到 124px，归一化**白省 17px**，否则被迫缩字号 |
| **班次名宽度自适应** | 超宽降 pt（下限 20）+ 块中心平移 | 班次名长度不受控（最长实测 `9DP0(验车)` 188px 块宽），必须保证不撞标签、不出屏 |
| **字段缺省即无排班数据** | 数据源省略 `shift` / `am` / `pm` 键 → 该天没有排班；取数层置 `blank_schedule=true`，四项落成空串，主区留白、底栏不画班次块 | 服务端用**省略键**表达「没排到班」（`docs/11` §5.5），既不是错误，也不是响应截断。把这种情况混同「获取失败」，正常的未排班日就会被显示成故障 |
| **拉取失败才显示「获取失败」** | 没有响应、业务码非 200、或响应无法解析且无可用缓存 → 传空串且 `blank_schedule=false`，主区左栏「获取失败」，底栏不画班次块 | 与「该天没有排班」是两件事。两者都表现为内容为空，所以判据由取数层按拉取结果设置 `blank_schedule`，渲染器不自行猜测 |
| **空内容不留空壳** | `shift` 空 → 不画反白块；`am` + `pm` 都空 → 不画「上午」「下午」前缀，区域留空 | 空串会被拼出「上午」两字、零宽文本会画出 36px 空白方块 —— 都是实测到的丑态 |
| **日期以数据源为准** | 收到 payload 时按 `date` 校准板载 RTC | 断网时 RTC 仍能提供日期（见 2.4） |

### 2.3 设备本地计算（不占数据源）

**判据：离线能算出来的放固件，会过期的东西走网络。**

| 项 | 来源 | 数据量 | 说明 |
|---|---|---|---|
| 星期 | `date` 直接推 | 0 | 纯计算 |
| 农历 | 内置表 | **800 B**（200×`uint32`，1900–2099） | `lunardate` 的 `YEAR_INFOS`，已用 5 个春节锚点校验全中 |
| 节气 | 天文算法 | **0 表** | Meeus 低精度太阳视黄经 + 二分，约 50 行 C、任何年份通用 |
| 节日 | 内置表 | **约 200 B** | 公历 14 + 农历 10 + 规则日 3（母亲节/父亲节/感恩节） |

> ⚠️ **调休（法定节假日放/补班）不在这里** —— 那是国务院每年发布的**行政数据**，
> 内置就得每年重刷固件。目前 payload 里没有该字段，**所以暂不显示调休**；
> 将来要做，在 payload 加一个字段随数据下来即可。

#### 农历表的 C 端编码（转写固件时照此实现）

参照实现见 `tools/lunar_cn.py`，数据源 `lunardate` 0.3.0 的 `YEAR_INFOS`（公认 lunarInfo 表，1900–2099 共 200 项）。
**年表不要手抄**：用 `tools/gen_lunar_table.py` 从 `lunardate` 导出 `cal_lunar_table.c`（含春节 5 锚点、闰月 4 锚点、
编码取位自洽、全域 73 019 天往返四项自校验）。

| 位段 | 含义 |
|---|---|
| `bit[3:0]` | 闰月月份 `L`，`0` = 该年无闰月，`1..12` = 闰几月 |
| `bit[15:4]` | 12 个月月长：**`bit15` = 正月**、`bit14` = 二月 … **`bit4` = 腊月**；`1` = 30 天、`0` = 29 天 |
| `bit[16]` | `M`，有闰月时该闰月的月长（`1` = 30 天 / `0` = 29 天） |

> ⚠️ **是 MSB→正月，不是 LSB→正月。** 本文件 2026-10-14 之前写的是「LSB 对应正月」，**已证实是错的** ——
> 以 `lunardate` 源码 `_enum_month()` 的 `days = (year_info >> (16 - month)) % 2 + 29` 为准：
> `month=1` 时取 `bit15`，`month=12` 时取 `bit4`。照错的写法转 C，`正月` 和 `腊月` 的月长会互换，
> 农历会**整体错一天**（大月小月的分界点错位）。年表源码注释里的位图也是这个方向：
> ```
>   bit#  1 111111000000 0000
>         6 543210987654 3210
>         M 123456789012   L
> ```

- 基准：**1900-01-31 = 农历 1900 正月初一**。
- 年长 = `348 + 各月多出的 1 天 + 闰月长`；实现上等价于 `lunardate` 的 `year_info_to_year_day()`。
- 闰月**紧随同名正常月之后**（如闰六月排在六月与七月之间）。
- 除夕判定用「明天是否正月初一」，不查表。
- **闰月不过节**：节日表按月份匹配时跳过闰月。
- 节日表 = 公历 14 项 + 农历 10 项 + 规则日 3 项（母亲节 5 月第 2 个周日 / 父亲节 6 月第 3 个周日 / 感恩节 11 月第 4 个周四）。
- ⚠️ `festivals(d)` 返回**全部**命中项（按 `FEST_PRIORITY` 降序），`festival(d)` 只是取首位的兼容包装 —— **展示层必须用 `festivals()`**。
- 排序是**稳定排序**、同分保持探测顺序（除夕 → 农历节 → 公历节 → 规则日）→ C 端复刻时必须用「严格小于才交换」的插入排序，否则同分项的先后会漂、顶栏签的左右位置就变了。

### 2.4 断网兜底

当前离线刷新模式下班次与时段留空；本节故障处理规则用于接入真实班次接口后的运行流程。

payload 拿不到时：

| 项 | 行为 |
|---|---|
| 日期 | 用板载 **PCF8563 RTC**（addr `0x51`，INT `GPIO5`）。驱动读时间时会检查 **VL 电压低标志** —— 置位说明 RTC 断过电、时间不可信，需重新对时 |
| 星期 / 农历 / 节气 / 节日 | **照常算**（全是本地计算，不依赖网络） |
| 时段 / 班次 | ① 先用本地缓存（若拉的是滚动窗口，当天数据大概率已在缓存里）；② 完全无缓存 → 主区左栏显示「获取失败」，底栏不画班次块 |

**重试策略（已定）**：首次失败后**间隔 1 分钟重试，最多 3 次**。
三次全失败则本次放弃，等下次唤醒（按键 / 次日 00:00）再试。

这也是把农历/节气放固件的额外好处：**断网时整页仍然基本可用** ——
日期走 RTC、历法信息照算，只有时段和班次受影响。

### 4.1 固件端选字号：在已有 pt 组里取**最大满足**，不是复刻二分

⚠️ **不能复刻那个二分。** 它的搜索区间是 `6..400`，二分**路径上**会访问 41 / 54 /
104 / 203 这类大 pt —— 单是 pt203 的中文点阵每字就要 5 KB（33 字 ≈ 170 KB），字库会爆。

固件端 `cal_font_pick_pt(utf8, target_h)`（`app/components/cal_font/cal_font.cc`）：

```
在 kCalFontGroups 的全部 pt 组里扫描，取满足下面**全部**条件的**最大 pt**：
  ① 该组能**完整画出**整串（missing == 0）
  ② 整串度量盒高 ≤ target_h
都不满足 → 返回 -1（调用方降级：不画 / 换占位文案）
```

判据 ① 与 PC 侧 `Canvas.font_for_height()` 用的是同一个量（`textbbox` 的 `b[3]-b[1]`），
所以只要该组画得全，结果就与二分等价 —— `python tools/pt_census.py --verify` 用
**7 469 例**验证过这一点（全部区域的全部签名 × 全部 target_h 档）。

#### 🕳 两条判据缺一不可（2026-10-14 板端自检抓出的真 bug）

初版实现是「沿 `kCalFontGroups` 顺序取**第一个**满足 `height ≤ target_h` 的组」，
并且注释里断言「组按 pt 降序排列」——**两处都错**：

| # | 错误 | 后果 |
|---|---|---|
| ① | 字库数据实际是 pt **升序**（`14 15 16 … 44 72`），不是降序 | 取到的是**最小**满足 pt，整页字号全线塌到 pt14（`2026年9月23日` 应为 pt28、`八月十三` 应为 pt21） |
| ② | 没判 `missing == 0` | 缺字不进包围盒（B 方案）⇒ 剩几个字单独算出的高度**虚小**，让一个根本画不全的组轻易满足条件 |

**发现途径**：板端 `RunFontSelfCheck()` 的 10 例 `font pick check` 报 **9 mismatch**
（10 例里唯一「通过」的那例是因为它的正确答案本就是最小 pt）。宿主侧 `--verify` 没抓到，
因为它证明的是「候选集查找 vs 二分」的**数学等价**，前提是「候选集内每组都能画全该串」——
而这个前提在固件侧**不成立**（每组字符集不同）。⇒ 等价性验证只是**必要条件**。

**现在的防回归**：`tools/font_missing_test.cc` 用例 ⑤（10 例选字号 + 取最大 + 各种负例）
与板端同源 10 例；实现显式取 max，与数据排列顺序**解耦**（顺序再变也不会退化成取最小）。

### 4.2 固定 pt 的区域（不随内容漂移；两处为逐档降级区间）

| 区域 | pt | 字符集 |
|---|---|---|
| 主区 休息日「休息」 | **72** 固定 | 休息 |
| 竖排星期 | **44** 固定 | 星期一二三四五六日（9 字） |
| 竖排节气 | **31** 固定 | 24 节气名去重 |
| 底栏 班次名 | **20–28** 逐 1 降级 | 半角字母/数字/`()-:` ＋ `休息` ＋ `绿`/`验车`/`值班`（见 §3.0 词表） |
| 顶栏 节日反白签 | **14–18** 逐档降级（先缩内边距后缩字号） | 全部节日名用字 ＋ 农历字 ＋ `·` |
| 底栏 标签「今日班次」 | 走墨迹高路径，target_h 23 → pt23 | 今日班次 |

> 逐字绘制的两处（星期 / 节气）**必须**用固定 pt —— 按墨迹高会给「一」选到 pt95
> （它只有一根横画，"墨迹高"其实是笔画**厚度**），「二」pt53、「三」pt48 同理。
> 反白班的班次名走 `text_width_pt` 逐 1 降级（不是墨迹高），同样只需要固定 pt 的点阵。

### 4.3 缺字策略：就地跳过（B 方案 · 2026-10-14 定）

绘制路径**永不终止进程**。`cal_text_layout()` / `cal_text_cursor_next()` 遇到字库
没有的码点（或非法 UTF-8 字节）时：

| 行为 | 说明 |
|---|---|
| **不画** | 该字不产生任何墨迹，也不进包围盒 |
| **笔位前进半字宽** | `CAL_MISSING_ADVANCE_PX(pt) = pt / 2`（全角汉字在 pt 下的步进 ≈ pt） |
| **计数上报** | `CalTextMetrics.missing` / `CalTextCursor.skipped` + `first_skipped` |

结果：写错一个字的代价是「两个字符之间多一个缝」，其余字符位置完全不变。

> 为什么不用「整块换安全文案」：那样一次脏数据的代价从「一个缝」变成「整栏信息丢失」，
> 而且无法从画面上看出是哪个字出的问题。跳过 + 日志更可诊断。
>
> 为什么不用「取数时先校验、不合格就丢掉括号备注」：会在**取数层**引入一份与字库
> 同步的副本词表，多一处需要维护的真源；现在把判断留在唯一知道字库内容的地方。

**三道启动期守卫**（字库漂移不靠运行期 abort 兜）：

| # | 位置 | 内容 |
|---|---|---|
| ① | `tools/font_verify.py` | `missing_chars()` **字符级断言**（所有用例） |
| ② | `tools/pt_census.py` | `check_shift_vocabulary()` **形态表 ↔ 字符集双向检查**，普查前跑 |
| ③ | `app/main/app_main.cc` | `kShiftForms` **板端词汇守卫**（10 形态 × pt20–28 共 90 项） |

**验证**：

```bash
tools/.venv/Scripts/python.exe tools/font_missing_test.py   # 宿主侧 30 项断言
```

用宿主 g++ 直接编 `app/components/cal_font/cal_font.cc`（纯逻辑，`esp_log` 由
`tools/stub/` 的替身接住）。判据是**结构性的**、不是与 Pillow 比对 —— 因为 Pillow
有那个字的字形、会照常画出来，没法作为「跳过」的参照：

- `9DP1(值班)` @pt28 → **150×30, missing=0**
- `9DP1(值班早)` @pt28 → **164×30, missing=1**（+14 = pt28/2，高度不变）
- 逐字游标：缺字之前的 7 个字形码点与笔位**完全相同**，右括号整体右移 14
- 退化输入：整串缺字 / 字号组不存在 / 空串 → 一律返回 `false` 且**不终止进程**
- 截断的 UTF-8 序列 → 2 个脏字节计入缺失，仍能算出包围盒

⚠️ `cal_font_data.c` 必须用 **gcc 按 C 编**（不能交给 g++）：C 里文件作用域的
`const size_t kCalFontGroupCount` 是外部链接，C++ 里是内部链接，混编会 undefined reference。

### 4.4 普查必须同时覆盖「**量宽**」用到的 pt（2026-10-14 补）

普查一开始只收集「**绘制**」用到的 (pt, 字符)，漏了「**测量**」—— 于是移植渲染器时
踩到第一颗雷：`build()` 用 `text_width_pt(date_cn, **27**)` 量标题宽度来定节日签行的
左界，而标题本身是按墨迹高 27 选中 **pt28** 画出来的。**量的 pt 与画的 pt 不是同一个。**

当时 pt27 组里只有数字（它是由别的内容在 target_h=27 下命中的），年月日缺失 ⇒
`cal_text_width_pt(27, date_cn)` 把缺字排除在包围盒之外、量出的宽度**虚小** ⇒
签行预算 `avail` 变大 ⇒ 最坏情形 `2031-10-01`（中秋 + 国庆，两个 3 字节日）**少降一档**，
签行比定稿宽 5px。是 `tools/cal_render_test.py` 的逐像素比对报出 **880 px 差异**才发现的。

修法：`tools/pt_census.py` 增设 `MEASURE_REGIONS`，按**字面 pt** 收集字符集
（`scan_literal_pt()`）——

| 区域 | 字面 pt | 字符集 |
|---|---|---|
| 顶栏 年月日（量宽） | **27** | 全部日期串（73 049 串 → 签名去重 364 个） |

> ⚠️ 不能复用墨迹高那条路径（`scan_ink_height`）：它会先把 target_h 折算成实际 pt
> （27 → 28），于是 pt27 永远收不到日期字符 —— 而渲染器偏偏要量 pt27。
>
> 收缩循环里对农历 / 「获取失败」/ 时段逐档量宽用的 pt，都落在各自墨迹高区域已覆盖的
> 集合内（量宽的 h 域 ⊆ 普查的 hs 域），故无需重复登记；**新增任何 `text_width_pt(…, 字面 pt)`
> 调用时，必须同步往 `MEASURE_REGIONS` 里加一行。**

### 4.5 渲染器移植与**逐像素**验收（2026-10-14）

固件侧渲染器 = `app/components/cal_render/`（**零 ESP-IDF 依赖**，只用 cal_font +
cal_almanac + stdint/stddef）。刻意不依赖 IDF 头，是为了能用宿主编译器编一遍，
和 Python 权威渲染器比**最终 15000 字节帧**：

```bash
tools/.venv/Scripts/python.exe tools/cal_render_test.py     # 17 用例，全帧零差异
```

| 项 | 做法 |
|---|---|
| 画布 | 自建 `CalFrame`（400×300、1bpp、MSB-first、**1=白/0=黑**）—— 与 `zectrix_epd_refresh_full_1bpp()` 格式**逐位相同**，渲染结果直接送屏，无转换 |
| 复用 | 位图布局与 `zectrix_demo_ui::ZectrixCanvas` 一致，设备侧传 `ZectrixCanvas::data()` 即可；不额外分配 15 KB |
| 判据 | 逐用例**逐字节**比对 C 帧 vs Pillow 的 `img.point(…, "1").tobytes()` |
| 覆盖 | 节气 / 无节气无节日 / 节日 / 春分=龙抬头 / 立春=春节 / **清明让位** / **两个 3 字节日（最坏签行）** / 双节日混合 / 除夕+情人节 / **休息日** / **拉取失败** / **夜班**（前缀按开始时间）/ **全角括号归一化** / **单段时段** / 已带前缀 / 最宽标题 / 春节 |

⚠️ 两个坑（都在 2026-10-14 踩到，已修）：

1. **量宽 pt 缺失**（见 §4.4）→ 880 px 差异。
2. **用例不要走命令行传中文**：Windows 上 `argv` 按 ANSI 代码页（GBK）编码，程序里
   拿到的已经不是合法 UTF-8 ⇒ 字库查不到字形 ⇒ 所有带中文的用例都被当作「缺字跳过」
   画不出来，看着像渲染器的 bug。现在用例走 **UTF-8 文件**（`cases.txt`）。

板端另有 `RunRenderSelfCheck()`：对 6 个固定日期复算渲染并比**黑像素总数**
（期望值取自 PC 权威渲染器的同一帧）。PC 侧证的是「同一份源码 + 同一份字库 → 同一张图」，
板上这一项证的是**烧进设备的这份二进制**确实产出同一张图 —— 节气用 double，
而 S3 **没有双精度 FPU**（软件模拟的 libm 与 PC 不同源）。

## 6. 时间基准与取数策略（已定）

### 6.1 RTC vs NTP —— 已定「RTC 走时 + 用 HTTPS 响应头校准」

板载 **PCF8563**（I²C addr `0x51`，INT `GPIO5`），驱动已具备：读写时间、**Alarm 中断**、
1 Hz 倒计时 Timer，且 `GetTime()` 会检查 **VL 电压低标志**（置位 = RTC 断过电、时间不可信）。

| | 板载 RTC | NTP |
|---|---|---|
| 精度 | 取决于 32.768 kHz 晶振：±20 ppm ≈ **每月 ±53 秒 / 每年 ±10 分钟** | 毫秒级 |
| 联网 | **不需要** | 必须 |
| 断网 | 正常走时 | 不可用 |
| 冷启动 | 备电耗尽后需重新对时（VL 标志可检测） | 联网即可 |

**对台历的影响**：日期错 = 农历 / 节气 / 星期 / 节日全错，所以**必须有校准来源**。
但 RTC 的年偏差是分钟级 —— **不会错到「跨天」**，只会让 00:00 的刷新时刻略偏。

**结论**：不单独发 NTP 请求。台历**每天本就要拉一次 HTTPS**，直接从**响应头的 `Date`
字段**取服务器时间校准 RTC 即可 —— **零额外请求、零额外依赖**。响应头缺失时才退化到 NTP。

> 首次开机（或 VL 置位）必须先成功校时一次，否则日期不可信。

### 6.2 拉取窗口 —— 已定「每天拉未来 14 天滚动窗口」

**单条记录体积**（实测）：JSON 紧凑 **82 B** / CSV **31 B** / 二进制结构 **28 B**。

| 窗口 | JSON | 二进制 |
|---|---|---|
| 7 天 | 595 B | 196 B |
| **14 天** | **1.19 KB** | **392 B** |
| 30 天 | 2.55 KB | 840 B |
| 365 天 | 31 KB | 10 KB |

**存储完全不是瓶颈**：原厂 `nvs`（16 KB）用二进制能存 **468 天**；
`assets` 分区（4 MB）能存 **120 年**。

**拉一段范围的收益**：

| 收益 | 说明 |
|---|---|
| **断网容错** | 当天的数据昨天就已到手，凌晨拉失败也不影响显示 |
| **减少请求** | 拉一次 14 天 vs 每天拉 1 次，请求量降到 1/14 |
| **不依赖「那一刻」联网成功** | 单一时刻失败不再致命 |

**代价 / 风险**：**临时换班、加班 → 缓存是旧的**。这是唯一实质风险。
对策：**每天仍拉一次**（滚动覆盖），而不是「拉一次用半个月」——
这样最迟第二天就会纠正；瞬时故障再靠 §2.4 的 1 分钟 ×3 重试兜住。

> **结论**：每天 00:00 拉一次**未来 14 天**，滚动覆盖本地缓存。
> 存 14 天仅 0.4 KB（二进制），却换来「断网两周仍能正确显示」。

### 6.3 按键与休眠

| 场景 | 行为 |
|---|---|
| 日常无人操作 | 每天 00:00 由 PCF8563 ALARM 经 GPIO5 唤醒，刷新页面后进入 deep sleep |
| 深度休眠时短按正面 BOOT | GPIO0 EXT1 唤醒，刷新当天页面，保留 30 秒操作时间 |
| 醒来期间长按侧边上键 3 秒并松开 | 执行 esp_restart，重新绘制页面并设置零点闹钟 |
| 醒来期间一直按住侧边上键到 8 秒 | 执行 esp_restart 并进入配网模式，不必松开（见 `docs/12`） |
| 操作时间内持续按住 BOOT 或上键 | 操作时间延长到松开后的 30 秒 |
| 操作时间结束 | 保持 GPIO17 电池供电，恢复 deep sleep |

上键 GPIO39 仅在芯片醒来时生效；BOOT GPIO0 与 RTC GPIO5 同时作为低电平 EXT1 唤醒源。程序不调用原厂 Shutdown 或 CutBatteryPower。按键验证见 `docs/09-按键操作与验证.md`。

### 6.4 电池与续航预算

**电池（官方 wiki 规格页 + 商品页一致）**：**2000+ mAh** 充电电池（锂聚合物），Type-C 充电。
官方宣称续航 **1–3 个月**（商品页口径：「静态待机、每天同步一次的测试条件下 ≈ 3 个月」）。

> ⚠️ **可换电池的物理上限**：官方 FAQ 明确电池尺寸需 **< 75 × 50 × 5 mm**，玩家可自行更换该尺寸内的其他电芯。
> 500 µL 级的腔体 → **想加大容量只能在这个体积里找更高能量密度的电芯**，不能靠"塞一块更大的"。

#### 功耗基线（官方 datasheet）

| 状态 | 电流 | 来源 |
|---|---|---|
| ESP32-S3 deep sleep（RTC 内存 + 外设） | **8 µA** | Espressif 技术手册 |
| ESP32-S3 deep sleep（仅 RTC 内存） | 7 µA | 同上 |
| ESP32-S3 light sleep | 240 µA | 同上 |
| **N16R8 的 8 MB Octal PSRAM（light sleep 附加）** | **+140–200 µA** | 实测文献 |
| 4.2" 400×300 墨水屏 全屏刷新 | 26.4 mW / 4 s | 同规格模块规格书 |
| 4.2" 墨水屏 待机（双稳态） | ≤0.017 mW ≈ **5.2 µA** | 同上 |

⚠️ **芯片 8 µA ≠ 整机**：还要叠加墨水屏待机 5.2 µA、LDO 静态、充电检测分压（`GPIO2/1`）、I²C 上拉。
→ 纸面 **20–30 µA**，**实板常见 30–100 µA**。

#### 本项目每天的耗电预算（按 §6.1 / §6.2 策略：每天唤醒 1 次）

| 项 | 每天耗电 |
|---|---|
| 静态待机（取 deep sleep 整机 50 µA） | 1.20 mAh |
| 唤醒 1 次：连 AP + DHCP + TLS + GET（≈8 s @ 100 mA） | 0.22 mAh |
| 全屏刷新 1 次（26.4 mW @ 3.3 V ≈ 8 mA × 4 s） | 0.01 mAh |
| ⚠️ **电池自放电（按 2 %/月）** | **1.33 mAh** |
| **合计** | **≈ 2.76 mAh/天** |

**→ 2000 mAh / 2.76 mAh ≈ 725 天 ≈ 2 年。**
（不算自放电是 1.43 mAh/天 → 3.8 年；按实板 20–100 µA 波动，合理区间 **1.4–2.7 年**。）

> 🔑 **两个反直觉结论**：
> ① **静态漏电 + 自放电合计占了每天的 ~90%**，刷屏只占 0.4% —— 优化靶子是**压静态电流**，不是减少刷新次数。
> ② **电池自放电（2 %/月）单项就占 48%**，是预算里最大的一笔。这意味着**就算把整机降到 0 µA，也撑不过 2.5 年**。

#### 与官方宣称口径的差异（须知）

官方「3 个月」反推 → **22.2 mAh/天 ≈ 926 µA 平均**；「1 个月」则 ≈ 2.8 mA。
这比上表的 2.76 mAh/天（≈115 µA）**高 8–24 倍**。差异来源：官方场景包含**待办同步 + 语音交互 + 状态灯**等本机没有的活动，且厂商宣传留有余量。

> 两条都成立：**官方数字偏保守**，本机场景**确实更省**。但 3–5 倍的纸算/实测偏差很常见 ——
> **以实测为准**（µA 档串电池正极，注意表内阻压降；最好用专用功耗分析仪）。

### 6.5 取数的实现形态 —— 板子里是 C，python/node/curl 都在 PC 侧

**结论：固件里 `python` / `node` / `curl` 一个都用不了，只有 C。**

ESP32-S3 上跑的是编译好的固件二进制，本项目走 **ESP-IDF（C/C++）** —— 因为要复用官方那套 C 组件
（`zectrix_epd` / `zectrix_board`），换 MicroPython 就全丢了，且 RAM/Flash 开销不划算。

| 角色 | 跑在哪 | 说明 |
|---|---|---|
| **`esp_http_client` + `esp-tls`(mbedTLS)** | **ESP32 固件里** | 唯一的正式路径，C |
| `curl` | PC | 调试接口最快的手段，**不上板** |
| `python` | PC | 写验证脚本、批量比对；**不上板** |
| `node` | PC / 服务器 | 同理；**ESP32 上没有 Node 运行时** |

> `libcurl` 理论上能交叉编译进 ESP32，但体积大、依赖重，没必要 —— `esp_http_client` 是官方组件，
> 底层同样走 mbedTLS，还自带重定向/超时/分块读取。**别绕远路。**

### 6.6 取数实现与自检（2026-10-26 完成）

接口细节、请求头、重试与三态判定见 **`docs/11` 第 9 节**。这里只登记与台历页有关的落点：

| 项 | 位置 |
|---|---|
| 组件 | `app/components/cal_sched`（解析与缓存纯 C，HTTP 与 NVS 走 IDF） |
| 页面数据来源 | `app/main/app_main.cc::RenderTodayPage` → `ResolveSchedule()` |
| 缓存格式 | 1108 字节 blob，NVS `cal_sched` / 键 `days`，每天覆盖一次 |
| 校时 | 云函数响应头 `Date`，差异超过 5 秒才写 PCF8563 |
| PC 侧验收 | `tools/.venv/Scripts/python.exe tools/sched_parse_test.py`（175 项断言） |
| 板端验收 | 每次唤醒打印 `sched self-check: ... N mismatch`，N 必须为 0 |

#### 两种架构（语言分工因此不同）

| 方案 | 链路 | 板子里 | 中间层 | 业务 key 存哪 |
|---|---|---|---|---|
| **A · 直连** | ESP32 ──HTTPS──▶ 第三方 | C | 无 | ⚠️ **烧进固件** |
| **B · 中转** | ESP32 ──HTTP──▶ 自有服务（Python/Node）──HTTPS──▶ 第三方 | C | 才轮到 Python / Node | 服务器上，**固件里没有** |

**共同点：无论 A 还是 B，板子里永远是 C。** 只有 B 的中间层才涉及 Python/Node 的选择。

- **A 的优点**：无额外依赖、无需常开服务器、每天就一次请求，链路最短。
  **代价**：key 随固件走 —— 固件可被读出（`esptool read_flash`），等于把 key 交出去。
- **B 的优点**：**key 不进固件**；第三方换地址/改字段不用重刷设备。
  **代价**：多一个必须常开的服务（它挂了 → 台历取数全挂，比 A 多一个故障点）。

#### ✅ 结论：当前走 **A · 直连**（2026-09-23 定）

单设备、单 key、每天 1 次请求 —— **B 的收益（藏 key）换不回多一个常开依赖的成本**。
而且 B 恰恰在**最需要它工作时最脆弱**：中转挂了 → 台历取不到数。

> ⚠️ **先纠正一个常见误解：B 不等于「必须买服务器」。**
> 云函数 / Serverless 就能当中间层 —— Cloudflare Workers（免费额度 10 万次/天）、腾讯云函数、
> Vercel 等，**零运维、零固定成本**，本机每天 1 次调用连免费额度的零头都用不到。
> 所以 B **不是做不了，是眼下不值得**。

**将来切 B 的触发条件**（出现任意一条再考虑）：

| 触发条件 | 为什么 |
|---|---|
| key 权限变大（能查/改他人数据，泄漏后果不可承受） | 这时"key 不上设备"的价值才压过复杂度 |
| 设备要给别人用 / 卖出去 | 固件会离开你的手，key 等于公开 |
| 第三方接口频繁改字段、换地址 | 中转层改一下就行，不用每次重刷设备 |

#### A 方案下的 key 存放：**放 NVS，别硬编码**

| 做法 | key 是否出现在 `firmware.bin` | 换 key 要重编固件吗 |
|---|---|---|
| 硬编码进源码 | ⚠️ **是**（明文在 `.rodata`，`strings` 一扫就有） | 要 |
| **写入 NVS** | **否** | **不用** |

> 注意界限：NVS 只是**提高门槛，不是加密** —— 未开 Flash Encryption 时，`esptool read_flash`
> 读 NVS 分区仍能拿到明文。但本项目**红线是绝不开 Flash Encryption**（烧 eFuse 不可逆），
> 所以 NVS 已是此处能达到的最好状态：key 不随固件外流，且换 key 无需重刷。

#### C 端技术栈（本地 IDF **v5.4.4** 实测确认）

| 层 | 用什么 | 实测依据 |
|---|---|---|
| HTTPS | **`esp_http_client`** + `esp-tls`(mbedTLS) | `components/` 下有 `esp_http_client`、`esp-tls`、`mbedtls` |
| ~~libcurl~~ | **不用** | ❌ **IDF 组件目录里没有 libcurl**（官方不提供） |
| 证书 | `esp_crt_bundle_attach` | `components/mbedtls/esp_crt_bundle/` 存在；官方 `https_request` 示例就这么用 |
| JSON | **`cJSON`**（IDF 的 `json` 组件，v1.7） | `components/json/CMakeLists.txt` 注册 `cJSON/cJSON.c`，`INCLUDE_DIRS cJSON` |

**组件声明**（`app/main/CMakeLists.txt`）：

```cmake
idf_component_register(SRCS "main.c"
                       INCLUDE_DIRS "."
                       REQUIRES esp_http_client esp-tls json)
```

> **为什么不是 libcurl**：IDF 官方不提供该组件；即便手动移植，它体积大（>100 KB）、
> 为通用场景设计（大量嵌入式用不上的协议与选项），而 `esp_http_client` 专为嵌入式写、底层同样是 mbedTLS。
> **JSON 这半个猜对了** —— cJSON 确实是正解，而且 IDF 自带、无需第三方引入。

**官方参考示例**（可直接对照抄）：

- `esp-idf/examples/protocols/https_request/` —— HTTPS + `crt_bundle`，**最贴近本项目**
- `esp-idf/examples/protocols/esp_http_client/` —— 事件回调 / `HTTP_EVENT_ON_DATA` / `get_content_length`

**最小可用骨架**（API 名已逐个比对 `esp_http_client.h`）：

```c
#include "esp_http_client.h"
#include "esp_crt_bundle.h"
#include "cJSON.h"

#define API_URL     "https://…"        // TODO 待接口资料
#define API_KEY_HDR "X-Api-Key"        // TODO ⚠️ 字段名待大人确认
#define BODY_MAX    2048               // 14 天 × ~100 B，2 KB 足够

static char *fetch(const char *api_key, char *date_out, size_t date_len)
{
    esp_http_client_config_t cfg = {
        .url               = API_URL,
        .method            = HTTP_METHOD_GET,
        .timeout_ms        = 10000,
        .crt_bundle_attach = esp_crt_bundle_attach,     // 校验证书（别关）
    };
    esp_http_client_handle_t c = esp_http_client_init(&cfg);
    esp_http_client_set_header(c, API_KEY_HDR, api_key);

    if (esp_http_client_open(c, 0) != ESP_OK) { esp_http_client_cleanup(c); return NULL; }
    esp_http_client_fetch_headers(c);                    // int64_t，即 Content-Length

    char *date = NULL;
    esp_http_client_get_header(c, "Date", &date);         // ← §6.1 的 RTC 校准来源
    if (date) strlcpy(date_out, date, date_len);

    static char body[BODY_MAX];
    int n = esp_http_client_read_response(c, body, sizeof(body) - 1);
    body[n > 0 ? n : 0] = '\0';                           // 注意 n<0 的失败路径
    esp_http_client_close(c);
    esp_http_client_cleanup(c);
    return body;
}
```

解析侧（cJSON 1.7，`cJSON_GetStringValue` / `cJSON_ArrayForEach` 均可用）：

```c
    cJSON *root = cJSON_Parse(body);
    const cJSON *days = cJSON_GetObjectItem(root, "days");
    const cJSON *d;
    cJSON_ArrayForEach(d, days) {
        const char *date  = cJSON_GetStringValue(cJSON_GetObjectItem(d, "date"));
        const char *shift = cJSON_GetStringValue(cJSON_GetObjectItem(d, "shift"));
        const char *am    = cJSON_GetStringValue(cJSON_GetObjectItem(d, "am"));
        const char *pm    = cJSON_GetStringValue(cJSON_GetObjectItem(d, "pm"));
        if (!date) continue;                              // 缺 date 直接跳过（§2.4 兜底）
        /* …写入本地缓存… */
    }
    cJSON_Delete(root);       // ⚠️ 必须：cJSON 走 malloc，不删就漏
```

> ⚠️ **cJSON 三不要**：① 不 `cJSON_Delete` 会累积泄漏；② 忘了判 `cJSON_Parse` 返回 NULL
> （响应不是 JSON 时直接崩）；③ 别把 `cJSON_GetStringValue` 的返回值当稳定指针长期持有 ——
> 它指向 `root` 内部，`cJSON_Delete` 后即失效。**解析完立刻拷进自己的缓存**。

#### C 端落地要点（写 `app/` 时注意）

1. **官方 Demo 里没有 HTTP 客户端** —— 实测 `components/` 只有 4 个自研组件
   （`zectrix_board` / `zectrix_epd` / `zectrix_demo_ui` / `zectrix_self_test`），
   `dependencies.lock` 里也无 mbedtls / crt_bundle → 建 `app/` 时**必须自己声明**（写法见上方），不能指望现成的。
2. **TLS 握手吃 RAM** —— mbedTLS 握手峰值 **~30–45 KB**，缓冲建议留内部 RAM（别只指望 PSRAM）。
3. **证书校验** —— `crt_bundle_attach = esp_crt_bundle_attach` 内置根证书包（约 60 KB Flash）；
   调试期可临时跳过校验，**别带上线**。
4. **`Date` 响应头就是 §6.1 的校准来源** —— `esp_http_client_get_header()` 直接取，零额外请求。
5. **先验接口、再写固件** —— 用 `tools/api_probe.py`（见下）。

#### 配套工具 `tools/api_probe.py`

在 PC 上把接口验通**再**翻译成 C。理由：固件里调 HTTP 的试错成本极高（刷一次 + 抓串口 + 等窗口），
不该用它来验接口。

```bash
tools/.venv/Scripts/python.exe tools/api_probe.py --self-test           # 离线自检契约解析器
set ZECTRIX_API_KEY=xxx
tools/.venv/Scripts/python.exe tools/api_probe.py --url https://…       # 真打接口
```

它会一次性验三件事：**链路**（状态码 / 耗时 / 401-403 提示）、**契约**（4 字段齐否、时段格式、
窗口是否够 14 天）、**时间校准**（`Date` 头能否解析、与本机差多少）。失败按 §2.4 的 1 分钟 ×3 退避重试。
退出码 0/1，将来可挂进烧录前的检查。
