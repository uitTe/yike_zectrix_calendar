## 二、安装步骤（从零复现）

### 1. 克隆 ESP-IDF

```bash
cd "D:/development_tools/esp"
git clone -b v5.4.4 --recursive https://github.com/espressif/esp-idf.git esp-idf
```

- 含全部子模块（23 个），**耗时 37 分 30 秒**，落盘 **4.0 GB**
- 走代理时 RTT 高，子模块阶段最慢。本体 pack 447 MB。

### 2. 安装工具链（**必须用 PowerShell，不要用 Git Bash**）

```powershell
$env:MSYSTEM = $null
$env:IDF_TOOLS_PATH = "D:\development_tools\esp\espressif"
$env:IDF_GITHUB_ASSETS = "dl.espressif.com/github_assets"   # 换源，绕开 github releases
$env:PATH = "C:\Users\<你>\.workbuddy\binaries\python\versions\3.13.12;$env:PATH"
Set-Location "D:\development_tools\esp\esp-idf"
& ".\install.bat" esp32s3
```

`IDF_GITHUB_ASSETS` **只接受裸主机名**（不带 `https://`）—— 它用来替换 `https://github.com/`。
本机实测 `dl.espressif.com/github_assets` 速度很好（50 秒下完第一个工具链包）。

### 3. 补装 riscv32-esp-elf-gdb（**必需，见坑 4**）

```powershell
$env:IDF_TOOLS_PATH = "D:\development_tools\esp\espressif"
$env:IDF_GITHUB_ASSETS = "dl.espressif.com/github_assets"
& "D:\development_tools\esp\espressif\python_env\idf5.4_py3.13_env\Scripts\python.exe" `
  "D:\development_tools\esp\esp-idf\tools\idf_tools.py" install riscv32-esp-elf-gdb
```

> `install.bat esp32s3` 只装 esp32s3 相关工具，**不含 riscv32 gdb** —— 而 `export` 要求所有必需工具就位。

### 4. 日常使用：走项目包装器（**不要直接调 idf.py**）

```bash
# 包装器：tools/idf.py
cd D:/zectrix/zectrix_yike/firmware
PY="C:/Users/<你>/.workbuddy/binaries/python/versions/3.13.12/python.exe"

"$PY" ../tools/idf.py set-target esp32s3
"$PY" ../tools/idf.py build
"$PY" ../tools/idf.py -p COM5 -b 921600 flash
"$PY" ../tools/idf.py -p COM5 monitor
```

包装器自动处理三件事：清 `MSYSTEM` 族变量、设 `IDF_PATH`/`IDF_TOOLS_PATH`、**显式构造完整 PATH**。

## 三、踩坑记录（重点）

### 坑 1 · Git Bash 被 ESP-IDF 硬拒

**现象**

```
ERROR: MSys/Mingw is not supported. Use either the Windows Command Prompt or the
Windows PowerShell instead.
```

在 Git Bash 里跑任何 `idf_tools.py` 都会 `sys.exit`。

**根因**：`idf_tools.py` 的检测就是

```python
if 'MSYSTEM' in os.environ:
    ... 拒绝
```

Git Bash **会在每次启动子进程时重新注入 `MSYSTEM`**，所以 `env -u MSYSTEM` 也没用。

**解法**：改用 **PowerShell**（原生 Windows 环境，无 `MSYSTEM`）。
若必须在 bash 里工作，就走 `tools/idf.py`（Python 侧 `env.pop("MSYSTEM")` 彻底清掉）。

---

### 坑 2 · `IDF_TOOLS_PATH` 在激活后丢失

**现象**：`idf.py` 报找不到 Python 环境，错误信息里出现 `C:\Users\<你>\.espressif\...`（该目录根本不存在）。

**根因**：`activate.py --export` 生成的激活脚本内容**完全正确（全是 D 盘路径），但它不设置 `IDF_TOOLS_PATH`**。
而 `idf.py` 正是靠这个变量定位 Python 环境，缺失就回退默认值 `~\.espressif`。

**解法**：dot-source 激活脚本之后，**显式设回**：

```powershell
$env:IDF_TOOLS_PATH = "D:\development_tools\esp\espressif"
$env:IDF_PYTHON_ENV_PATH = "$env:IDF_TOOLS_PATH\python_env\idf5.4_py3.13_env"
```

---

### 坑 3 · **PATH 无法通过 shell 传给子进程**（最阴险）

**现象**

- PowerShell 里 `$env:PATH -match 'ninja'` → `True`
- `where.exe ninja` → 能找到
- `ninja --version` → `1.12.1`
- **但 cmake 子进程报**：`"cmake" must be available on the PATH`

**诊断过程**

用 Python 视角（即子进程真实看到的环境块）对比：

```
=== PowerShell 视角 ===
$env:PATH matches ninja: True

=== Python 视角（子进程实际看到的环境块）===
PATH_keys = ['Path', 'PATH']     ← 环境块里有两个同名键！
len = 945                         ← 只有系统路径
has_ninja = False                 ← 工具链不见了
```

**决定性证据**：测试普通变量能否传递 ——

```
PS : MYTEST=hello123 ; Path_has_ZZTEST=True
PY : MYTEST=hello123 ; Path_has_ZZTEST=False     ← 普通变量能传，唯独 PATH 被还原
```

**根因**：进程环境块里同时存在 `Path` 和 `PATH` 两个键（Windows 环境变量不区分大小写，但进程块里可以共存）。
父 shell 传递差异导致 cmake 读到的是**错的那个**（旧值）。
这是该 PowerShell 运行环境对 PATH 的特殊处理，**靠改 PowerShell 变量解决不了**。

**解法**：**不要依赖 shell 传递 PATH**。用 Python 显式构造 `env` 字典后交给 `subprocess`：

```python
env = dict(os.environ)
for k in ("MSYSTEM", "MSYSCON", "MINGW_PREFIX", "MSYS"):
    env.pop(k, None)

# 先把所有 PATH 变体收集起来，再统一成单个 PATH 键
existing = [env[k] for k in env if k.upper() == "PATH"]
for k in [k for k in env if k.upper() == "PATH"]:
    del env[k]

prefix = [PY_ENV_Scripts, IDF_TOOLS_Path, GitCmd]
env["PATH"] = os.pathsep.join(prefix + existing)

subprocess.call([PYEXE, IDF_PY, *args], env=env)
```

> ⚠️ **一个我自己写出来的 bug**：第一版实现是「先删键，再 `env.get("PATH")` 取旧值」——
> 等于先把要保留的值清空再读，拿到空字符串，工具链路径全丢。
> **必须先取出旧值，再删键。**

**这就是 `tools/idf.py` 存在的全部理由。**

---

### 坑 4 · `idf_tools.py export` 静默失败（返回码 1、无输出）

**现象**：包装器解析不到任何环境变量，`export` 的 stdout 长度为 0。

**根因**：**缺少 `riscv32-esp-elf-gdb`**。`export` 要求**所有必需工具**都已安装，
有一个缺失就整体失败（返回码 1），且**不打印是哪一个缺**。

**定位方法**：

```powershell
& $PY "D:\development_tools\esp\esp-idf\tools\idf_tools.py" check
```

**解法**：装它就完事（见「安装步骤 3」）。

---

### 坑 5 · 半成品 `build/` 让 `set-target` 拒绝执行

**现象**：cmake 报错，`set-target` 的 fullclean 拒绝执行。

**根因**：上一次失败的 cmake 配置在 `build/` 里留下残缺的 cache。

**解法**：

```bash
rm -rf build      # 纯构建产物，被 .gitignore 忽略，删了安全
```

---

### 坑 6 · GitHub Release 资源被代理隧道挡掉（502）

**现象**：`github.com` 网页和 `git clone` 都通，但下载 Release 二进制时 502。

**根因**：代理对 `objects.githubusercontent.com` 的隧道失败。

**解法**：走加速镜像前缀。

```bash
U="https://github.com/<owner>/<repo>/releases/download/<tag>/<file>"
curl -L -o out.bin "https://ghfast.top/$U"
```

本机实测 `ghfast.top` 可用。**ESP-IDF 工具链则用 `IDF_GITHUB_ASSETS` 换源。**

### 交叉验证：本地编译产物 vs 官方预编译镜像

官方 `zectrix-note4-epd-demo-v1.0.0.bin`（1,074,896 B）是**合并镜像**，分段比对：

| 段 | 偏移 | 结果 |

> 分区表一致这一点很有价值：说明本项目的 `sdkconfig` / 分区配置与官方发布版是同一套，
> 后续可以直接在本地产物上开发。
